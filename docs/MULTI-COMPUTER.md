# 多电脑部署与设备区分

当前版本支持每台电脑独立运行 Bridge、使用不同的飞书机器人。统一中转服务、设备注册和跨电脑消息分发尚未实现，本文后半部分是后续实现设计，不是可启用的配置。

## 当前怎么识别项目

消息的处理路径是：飞书应用（App ID）→ 对应 Bridge → 群 `chatId` → 本机项目 `cwd` → 该群或话题关联的会话。

- 群名和项目名方便人辨认，不是跨电脑路由依据；仅修改群名不会改变设备或目录绑定。
- `projects.json` 保存群 `chatId` 与本机绝对目录 `cwd` 的绑定，`sessions.json` 保存会话关联。这些文件按机器人保存在本机 `~/.feishu-codex-bridge/bots/<appId>/` 下。
- 当前没有用于跨电脑分发的设备 ID。两台电脑即使目录或项目名称相同，也有各自独立的代码、会话和运行状态。

对应实现：[项目注册表](../src/project/registry.ts)、[消息处理](../src/bot/handle-message.ts)、[本机数据路径](../src/config/paths.ts)。

## 现在可用：每台电脑一个独立机器人

| 电脑 | 飞书应用 | 机器人显示名示例 | 项目群名示例 |
| --- | --- | --- | --- |
| MacBook | 独立 App ID A | Codex-MacBook | MacBook｜哈尼网站 |
| Windows 台式机 | 独立 App ID B | Codex-Windows | Windows｜哈尼网站 |

两台电脑可以使用同一个飞书用户管理。关键是应用凭据不同；只把同一个机器人的名字改成两个名称，不能实现隔离。群中只加入负责该电脑的机器人。

在第二台电脑上配置：

1. 按 [README 的本地构建步骤](../README.md#本地构建)安装本仓库版本，并准备本机 Codex 与登录环境。
2. 运行 `node bin/feishu-codex-bridge.mjs bot init` 或通过本机网页控制台添加一个新机器人，确认其 App ID 与第一台电脑不同。按引导完成权限、长连接事件订阅与应用发布；入口参考 [上游安装说明](UPSTREAM-README.md)。飞书里的显示名在应用后台设置。
3. 私聊新机器人建立项目，绑定第二台电脑上真实存在的目录；建项目时使用带电脑前缀的项目名。相同 Git 仓库也需要在第二台电脑单独准备工作副本。
4. 需要本版完成通知时，按 README 在第二台电脑对新 App ID 执行 `setup:private`。需要账号热切换时，按 [热切换说明](../HOT-SWITCH.md)在该电脑单独配置账号和受管终端。
5. 启动第二台电脑的 Bridge，在其项目群发送只读任务，例如“报告当前工作目录和项目状态，不修改文件”，确认返回的是第二台电脑的目录。在第一台电脑的项目群做同样检查。

不要直接复制第一台电脑的整个运行目录作为第二台电脑的配置。凭据库与本机环境有关，目录、会话和账号状态也需要在目标电脑重新建立。共享源码不等于共享运行配置。

`/runtime`、`/runtime usage`、`/runtime switch <账号>` 目前仅供管理员在机器人私聊使用，作用于该机器人所连接电脑的本机 codex-switch；不会同步切换其他电脑。会话恢复也查询本机原生会话，不能通过复制一个 session ID 自动接入另一台电脑的会话。

## 为什么共用同一个机器人会出问题

飞书长连接使用集群分发：同一应用有多个在线客户端时，一条事件只会随机交给其中一个客户端，不会广播，也不会根据群名或群 ID 自动选择电脑。见 [飞书官方长连接说明](https://open.feishu.cn/document/ukTMukTMukTM/uYDNxYjL2QTM24iN0EjN/event-subscription-configure-)。

例如 MacBook 的项目消息落到 Windows Bridge 后，Windows 本机可能没有对应群的绑定：非 @ 消息可能被忽略，@ 消息可能提示未绑定。复制绑定也不能解决分发问题，反而可能让任务使用错误的本机目录。`allowedChats` 只能过滤已经收到的事件，不能把事件转发给另一台电脑。

因此，不要在两台电脑上同时运行使用同一 App ID 的 Bridge。迁移同一个机器人到另一台电脑时，应先停止原电脑上该机器人的 Bridge，再在目标电脑配置并核对绑定；原电脑恢复时也不要让两边同时上线。

## 待实现：一个机器人通过中转服务控制多台电脑

中转服务需要在一个稳定在线的位置运行，可以是云服务器，也可以是一台长期在线的电脑。各电脑主动建立到中转服务的加密连接，无需给每台电脑暴露公网入站端口。

```text
飞书应用（唯一事件接收端）
          │
          ▼
      中转服务
      ├── 群 A → device-mac → MacBook 设备端 → 本机网站目录
      └── 群 B → device-win → Windows 设备端 → 本机实验目录
          ▲
          └── 结果、图片与状态沿原群和原话题返回
```

未来路由应使用 `appId + chatId → deviceId + projectId`；项目在设备端解析到允许的本机目录。设备 ID 应是持久、唯一的标识；电脑显示名和群名可修改，不参与身份认证。会话关联还需带设备和项目标识，不能只凭 session ID 定位电脑。

实现至少需要覆盖：

- **设备连接与身份**：注册、独立设备凭据、撤销、在线状态与心跳；重连时防止同一设备身份被多个连接同时使用。飞书应用凭据保留在中转服务。
- **项目绑定与权限**：管理员明确选择设备和项目，设备校验目录及访问权限；不允许消息指定任意设备或任意本机路径。
- **消息与交互转发**：群消息、话题、卡片按钮、继续、停止、目标控制、附件和完成通知都需要保留原设备与会话关联。只转发任务文本不足以替换现有 Bridge。
- **交付与恢复**：请求 ID、去重和执行状态持久化；断线后先核对任务状态再重试。设备离线时明确提示，首版不默认排队执行，也不回落到其他电脑。
- **管理命令**：私聊与机器人菜单没有项目群上下文，`/runtime` 和切号等操作需要先选择设备并显示目标，不能根据最近使用的群静默推断。该设备选择入口目前不存在。

这是对现有 Bridge 接收事件与本机执行职责的拆分，需要新增协议、服务和设备端代码。仅部署一个 HTTP 反向代理或修改群名，不能获得上述能力。

上线前应验证：两台设备可运行同名项目；改群名不改变设备绑定；私聊管理操作选择正确设备；离线不误投；重连不重复执行；停止和卡片回调只影响目标会话；结果和图片返回原话题。完成这些实现和验证后，才能将“同一机器人跨电脑控制”标记为可用。
